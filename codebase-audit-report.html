01Executive verdict

This is a capable, feature-rich app built fast by one developer — and it shows in both directions. The domain modeling is genuinely thoughtful (reading-fluency pipeline, gamification economy, bilingual ESL support), the newer modules are well-factored, and there are several patterns worth being proud of. But the codebase carries the classic tax of solo velocity: every one of the 180 API routes hand-rolls its own auth, validation, and error handling, and that single missing abstraction is the root cause of most of the security and consistency findings below.

The headline risks are narrow and fixable: one critical account-takeover bug, a cluster of non-atomic / racy gamification writes, a few missing database indexes on hot paths, and an unhardened Whisper call at the center of the grading pipeline. None of these require re-architecting — they're targeted fixes. The larger, slower-burn theme is that type-checking and linting are switched off (79 real type errors hidden), there are no automated tests, and the app is almost entirely client-rendered, forfeiting the framework's biggest performance lever.

The single highest-leverage change

Introduce a withAuth(handler, { role, ownership }) route wrapper. Three of the five audits independently flagged its absence. Today: 239 getCurrentUser() call-sites, ~240 hand-rolled 401s, 267 inline role comparisons, 170 duplicated try/catch epilogues, and 0 routes using schema validation. This one abstraction would collapse that duplication and structurally prevent the IDOR, stack-leak, and inconsistent-logging classes of bug — you fix the pattern once instead of auditing 180 files.

03Security & authorization

180 routes, middleware is pass-through so each route self-checks. The ownership helpers that exist are good — the problem is inconsistent application.

CriticalTeacher can mint a login for any student in the school
The token-regeneration route checks role only, never class ownership, and returns the new token in the response. Combined with /s/[token] (which turns a token into a passwordless session), any teacher or admin can take over any student account school-wide. An ownership helper (userCanAccessStudentMedia) exists and is used elsewhere — it's simply not applied here. src/app/api/teacher/students/[studentId]/regenerate-token/route.ts:12–32
HighNo shared auth/validation/error abstraction across 180 routesflagged by 3 audits
239 getCurrentUser() call-sites, ~240 hand-rolled 401s, 267 inline role comparisons, 170 duplicated try/catch blocks, and zero routes using zod for body validation. This is the structural root cause of the inconsistencies below (401 vs 403, console.error vs logError, stack leaks, missing ownership checks). codebase-wide — canonical copy at src/app/api/fix-story-audio/route.ts:14–18
MediumUnauthenticated roster + visual-password-type leak
Two class-scoped routes return student names and visualPasswordType with no getCurrentUser() at all — even though the sibling /api/students route was explicitly hardened against exactly this. With only a classId (obtainable from /c/[shortCode]), the ~12-option visual-password keyspace is narrowed for brute force. src/app/api/classes/[classId]/students/route.ts:31–50 · .../[studentId]/route.ts:41–66
MediumNo rate limiting on password login or magic/short-link entry
Teacher/admin email-password login, /s/[token], and /c/[shortCode] have no throttle or lockout (only bcrypt cost 12 slows password guessing). The good per-student + per-IP rate limiter built for student-login isn't applied to these paths. src/app/api/auth/login/route.ts · src/app/s/[token]/route.ts · src/app/c/[shortCode]/route.ts
MediumStack traces / internal errors leaked in responses
Several routes return error.message and even error.stack in the JSON body (syllabus, bulk-import, multiple reading routes). Authenticated-only, but leaks DB/internal structure. src/app/api/classes/[classId]/syllabus/route.ts:69,121 · .../bulk-import/route.ts:66 · several teacher/reading routes
MediumPresigned upload: shared namespace, unsanitized key, no size cap
Any authenticated user (incl. students) can request a presigned PUT. filename is interpolated into the key unsanitized; type='tts' keys have no per-user scoping (a student can write into the shared classroom-TTS namespace); and no content-length-range means no upload-size limit. src/app/api/upload/presigned-url/route.ts:45 · src/lib/storage/r2-client.ts:257–267

04Database & data layer

Schema is thoughtful on newer tables (documented composite/partial indexes) but has hot-path gaps and a cluster of non-atomic gamification writes.

HighMissing indexes on the hottest foreign keys
The classes table has no index block at all — teacher_id, school_id, term_id are unindexed, yet accessibleClassIds() filters on teacher_id on essentially every teacher/admin request (seq scan). Separately, class_enrollments.student_id has no standalone index (the only index is composite with classId leading), so every student dashboard / classmates lookup seq-scans enrollments. src/lib/db/schema.ts:218–251 (classes), 253–264 (enrollments) · src/lib/auth/class-access.ts:115–121
HighawardXp: non-atomic writes + lost-update race
Two distinct defects in one function. (a) It inserts the XP event, upserts progression, inserts unlocks, and loops N star-writes outside any transaction — a mid-sequence failure leaves XP events without a balance bump, or XP updated but stars diverged. (b) It reads progression into JS, computes new totals in memory, and writes absolute values back — so two concurrent awards clobber each other (last-write-wins), losing XP and corrupting level/streak. Notably awardStars uses sql increments and is race-safe; XP is not. No caller wraps the domain write + awardXp together either. src/lib/gamification/award.ts:62–222 (reads :74–84, absolute writes :136–145)
High/api/recordings GET is unbounded and over-selects
Returns every recording across every class a teacher manages — no LIMIT, no pagination — and joins stories to select the full storyContent body for each row, which the submissions client never uses. Grouping happens client-side. Grows linearly with history. Admin list endpoints (users, stories, students) are likewise unpaginated, while /api/stories paginates correctly — so the pattern exists, just isn't applied. src/app/api/recordings/route.ts:145–191
MediumMigration journal out of sync + duplicate 0007
The Drizzle journal ends at idx 49, but the folder contains 0050–0054 (multibook, teacher-capabilities, generated-tests, longitudinal-progress, gradebook). These were applied out-of-band with IF NOT EXISTS guards, so a fresh environment running drizzle-kit migrate would be missing those tables. Two files also collide on the 0007 prefix. migrations/meta/_journal.json vs migrations/0050–0054 · 0007_add_story_tts_versions.sql
MediumFK relationships modeled as unconstrained jsonb / magic strings
reading_passages.target_vocab_ids is a jsonb array of vocabulary.id UUIDs — no FK, no cascade, no index; deleting a vocab row silently dangles references. Separately, book_slug is used across practice/test/curriculum tables but the books table has no slug column at all — the catalog is disconnected from everything keyed to it. src/lib/db/schema.ts:1487–1490, 1746 · 947, 1012, 1040 vs books 638–657
MediumOther data-layer gaps
N+1 in /api/teacher/classes GET (one COUNT per class — the dashboard already shows the right GROUP BY pattern); student dashboard leaks assignments from teacher-archived classes (no classes.active filter); no request-level memoization of hot lookups (getCurrentUser, accessibleClassIds, capabilities recomputed per call, not wrapped in React cache()); non-transactional lazy class/school provisioning can orphan a school. teacher/classes/route.ts:55–67 · student/dashboard/route.ts:86–96 · auth.ts:119–137

05AI pipeline & integrations

The grading pipeline's durability model is genuinely good (recordings are always safe and re-gradable). The gaps are resilience, cost reuse, and a bug that crept in through copy-paste.

HighWhisper client has no timeout and no retry/backoff
The most cost- and latency-critical external call is a bare fetch with no AbortController and no retry loop — a hung request blocks indefinitely, a 429/5xx blip fails the whole submission on the first shot. Conspicuous because both image clients implement 3-attempt exponential backoff. ElevenLabs client has the same gap. src/lib/grading/whisper-client.ts:47 · src/lib/tts/elevenlabs-client.ts:53
MediumPassage pipeline drops the Mandarin summary (copy-paste drift)
The two recording pipelines (assignment vs passage-page) share the pure scoring core but duplicate ~25-column persist blocks. The copy diverged: the passage persist sets teacherSummary but omits teacherSummaryZh even though the value is computed and the column exists — so Taiwanese teachers reviewing passage-page recordings silently never get the Mandarin summary. A duration type mismatch (integer vs decimal-string) exists between the two too. src/lib/grading/analyze-recording.ts:522 (missing) vs :319–320 (present)
MediumCost waste: re-grade re-transcribes; passage TTS regenerates every page
Every teacher "Re-analyze" click re-runs Whisper from scratch even though the transcript is already stored on the row — pure billed waste if the intent is a re-score. Passage-page TTS re-synthesizes and re-uploads all pages with no "already has audio for this voice" guard, and the R2 key omits speakingRate so a rate change silently overwrites. No per-student/day cap on any expensive call (Whisper, Claude, image-gen). analyze-recording.ts:389,175 · teacher/reading/passages/[passageId]/audio/route.ts:105–140
MediumRecordings analysis has no job-status tracking; failures can vanish
Unlike the reading-generation pipeline (which has proper queued→running→completed/failed job rows), the recordings pipeline has no analysis-state column. If the background task is killed before persistFailure runs, the row stays status='submitted' with null analysis — indistinguishable from "still processing," with no teacher-visible stuck/failed signal. Also: several fire-and-forget routes set no maxDuration despite dispatching multi-second work after the response, and the code contains contradictory assumptions about whether the deploy target is long-running Node or serverless. src/lib/grading/analyze-recording.ts:435–437 · recordings/upload/route.ts (no maxDuration)
MediumScattered model IDs; fragile background-strip; orphaned R2 objects
claude-sonnet-4-6 is hardcoded in 8+ files with no central constant (an upgrade touches all of them). stripGeminiBackground is a hard-coded-tolerance flood-fill with known failure modes that only console.warns (a 0-pixels-stripped result still ships an opaque avatar). Deleting a story removes the row but never deletes its TTS/image objects from R2 — orphan-by-design in several entity types, with a "needs a sweep" comment and no janitor job. Some Claude callers set thinking: disabled and effort: medium together (contradictory). 8+ files · src/lib/generation/avatars.ts:47–117 · src/app/api/stories/[id]/route.ts:198–201

06Frontend & client performance

45 of 48 pages are 'use client' doing useEffect+fetch. There is no server-side data fetching, no data library, and no next/dynamic anywhere — this is the root cause of most findings here.

HighAlmost entirely client-rendered; ~40 hand-rolled fetch/loading blocks
39 pages fetch inside effects with hand-rolled useState+loading flags; only 6 parallelize with Promise.all. No SWR/React Query, no RSC data fetching, no code-splitting. This forfeits the App Router's streaming/caching and produces client waterfalls on every screen. src/app/**/page.tsx (grep: 0 hits for swr/react-query/@tanstack/next-dynamic)
HighRoot AuthProvider gates the whole app in a client effect and re-renders on every navigation
The entire tree is wrapped by a client component that fetches /api/auth/me after hydration and runs role-redirect logic in an effect keyed on pathname. Consequences: flash/redirect churn on load, RBAC enforced only client-side via pathname.startsWith, and the context value is not memoized while usePathname() re-renders the provider on every route change — so all consumers re-render each navigation. src/components/providers/auth-provider.tsx (mounted src/app/layout.tsx:19)
HighStudent landing page eagerly bundles all 5 spelling games + confetti
The V2 dashboard imports all five game components (~3,100 lines, 4 importing canvas-confetti at module top) at the top level — all ship in the bundle before a child picks a game, on the hot path for young learners on tablets. Textbook next/dynamic case. Compounding this, the legacy 828-line dashboard still mounts and fires two wasted fetches before redirecting to V2. src/app/student/dashboard-v2/page.tsx:31–35 · src/app/student/dashboard/page.tsx
MediumLarge duplicated component families
Five spelling games (~3,100 lines) each reimplement the same game loop (fetch next word, submit result, audio playback, confetti, streak state) — a useSpellingGame hook could remove ~1,000+ lines. Two MediaRecorder implementations exist where one useMediaRecorder hook would do. A well-built shared TTS hook (use-play-tts) exists but is used by exactly one component while 7+ others hand-roll new Audio(). src/components/spelling/*.tsx · audio-recorder.tsx + teacher-reply-recorder.tsx · src/hooks/use-play-tts.ts
MediumGiant page components; providers not memoized; raw <img> everywhere
Six pages exceed 800 lines doing state+fetch+UI inline (reading/generate has 34 useState). StarsProvider/AvatarProvider pass fresh context objects each render (re-render storms during avatar drags) and fetch on every student page load regardless of relevance. 47 raw <img> vs 7 next/image on an image-heavy young-learner UI (layout shift, no optimization). teacher/reading/generate/page.tsx (1535) · providers/*.tsx · grep 47×<img
Lowi18n / a11y gaps
Proper lang="zh-Hant" wrapping (so screen readers pronounce Mandarin correctly) exists only on newer V2 surfaces; older teacher/spelling components emit Chinese untagged. Generic alt text on comprehension images. Inconsistent loading-flag naming (loading/isLoading/saving/submitting…) since there's no shared data hook. src/app/layout.tsx:17 (lang="en") · spelling components

07Architecture & hygiene

HighType-checking and linting are switched off; 79 hidden errors; no tests
typescript.ignoreBuildErrors: true and a comprehensively-disabled ESLint config mean npm run build is not a correctness check. tsc --noEmit surfaces 79 errors across ~25 files. ~35 are two mechanical causes (react-hook-form/zod version skew + one mis-typed role union), but the 10 TS2367 errors in teacher/dashboard/route.ts — "comparison appears unintentional" on user.role !== 'admin' — look like a latent bug (dead admin branch or mis-typed union). No test runner is configured; the scripts/test-*.ts are manual harnesses hitting live AI APIs. next.config.mjs:4 · eslint.config.mjs:24–44 · src/app/api/teacher/dashboard/route.ts (7 lines)
MediumRoute- and surface-level duplication
The three media proxies (audio/images/media) are near-identical stream-and-serve handlers. Entities exist as parallel teacher/admin/public route families (stories at 3 paths, students at 3, classes at 3) differing only in access scoping — which belongs in a shared data layer. Admin routing is split across a (admin) route group and a literal admin/ folder, so the class list is at /classes but class detail at /admin/classes/[id]. src/app/api/{audio,images,media}/[...key]/route.ts · src/app/(admin)/* vs src/app/admin/*
MediumModule-organization confusion
src/lib/auth.ts (flat file) coexists with src/lib/auth/ (directory) — importers use both. Three separate "generate" pipelines (generation/, reading/generate/, practice/generate.ts) all call Anthropic and produce questions. "Avatar" means three different things across the codebase (AI catalog art, student character composition, legacy emoji picker) — a documented naming collision. src/lib/auth.ts vs src/lib/auth/ · src/lib/{generation,reading/generate,practice}
MediumConfig & logging hygiene
200 MB global Server Actions body limit (memory/DoS surface applied to every action; likely only uploads need it). No env-var validation module — 37 scattered process.env reads, missing keys fail at first request not boot. Logger is well-built and adopted in ~130 files, but 342 raw console.* calls remain (incomplete migration; bypasses secret redaction). A stray .env.production.backup sits in the repo root. next.config.mjs:8 · src/lib/logger.ts (partial adoption)

09What's done well

StrengthRecording durability & graceful degradation
Audio is written to R2 before any analysis and is fully re-gradable from R2; the pipeline is layered so a Claude/API-key failure returns null and still lands deterministic WCPM/bands/prosody. A hallucination guard skips the paid Claude call when the transcript is implausibly short. Recordings are never lost.
StrengthThe reading-generation pipeline is the model to copy
Cleanly staged (plan → prose → validate → questions → images) behind one barrel, with real job tracking (queued→running→completed/failed, per-passage results, retry lineage). This is exactly the job-status pattern the recordings pipeline lacks.
StrengthThoughtful security where it's applied
The sensitive R2 proxies (audio/media) enforce real ownership, return 404-not-403 to avoid a key-existence oracle, and set Cache-Control: private for minors' content. Centralized class-access helpers correctly handle co-teachers and are used by ~58 routes. Student-login has a genuine threat model (dual rate limiting, class-scoping). bcrypt cost 12, httpOnly+secure+SameSite cookies.
StrengthWell-engineered small pieces
The image-gen facade (clean provider abstraction, 5s settings cache, build-safe fallback). The logger with targeted secret redaction. The tiny, deliberate feature-flags module with a documented boundary. Spelling audio/image cost controls (skip-if-exists + cross-word reuse) — the reuse discipline the rest of the AI layer should adopt. Thoughtful reading-feature indexing (composite covering indexes, a partial unique index for one-session-per-student). Consistent kebab-case naming, real strict: true tsconfig, @/ path aliases, prompt-caching hygiene.
