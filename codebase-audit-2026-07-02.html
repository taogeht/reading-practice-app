1Executive verdict

This is a feature-rich, genuinely well-designed product with strong domain logic — the grading pipeline, reading-generation pipeline, and student-login threat model are better than most production apps. The debt is concentrated in three places: authorization consistency (one real IDOR, plus 180 routes each hand-rolling auth), duplication (no shared route wrapper, no data-fetching layer, five spelling games reimplementing the same loop), and disabled safety nets (type errors ignored at build, ESLint off, zero tests). None of it is architectural rot — it's the natural residue of fast solo iteration, and most of it is fixable with a handful of shared helpers.

✓ What you're doing right

  • Recording durability. Audio lands in R2 before analysis; every recording is fully re-gradable. The pipeline degrades gracefully — Claude failure still leaves deterministic WCPM/bands.
  • The reading-generation pipeline (src/lib/reading/generate/) is the most cohesive module in the tree: staged plan→prose→validate→questions→images with real job tracking (reading_generation_jobs: queued/running/failed, retry lineage).
  • Student-login threat model — dual per-student + per-IP rate limiting, enrollment verification to block school-wide targeting, well-documented reasoning.
  • Sensitive R2 proxies done properly — audio/media proxies resolve the owning student, gate via ownership helpers, return 404 (not 403) to avoid existence oracles, and set Cache-Control: private for minors' content.
  • Ownership helpers exist and account for co-teachers (src/lib/auth/class-access.ts) and ~58 routes use them.
  • Image clients have real resilience — 3-attempt backoff, transient-vs-SAFETY-block classification, and a 5s settings cache on the provider lookup.
  • Spelling audio/image cost discipline — skip-if-exists, cross-word/same-school reuse. Best-in-repo pattern.
  • Feature flags & v2-route migration strategy are clean, documented, and instantly reversible.
  • Session/crypto hygiene — bcrypt cost 12, httpOnly/secure/sameSite cookies, Web Crypto session IDs, real logout.
  • logger.ts with secret redaction; heaviest read paths (teacher dashboard, gradebook, student dashboard) correctly avoid N+1 via joined aggregates.

✗ What's biting you

  • One real security hole: any teacher can mint a working login token for any student school-wide (IDOR, full account impersonation of minors).
  • No shared route abstraction: 239 getCurrentUser() call sites, ~240 hand-rolled 401s, 170 copy-pasted try/catch blocks — the root cause of every per-route inconsistency found.
  • Zero zod in the API: 0 of 180 routes validate bodies with a schema.
  • Missing hot indexes: classes has no FK indexes at all, yet is scanned on nearly every teacher request; class_enrollments.student_id can't use its composite index on every student page.
  • 45 of 48 pages are 'use client' with hand-rolled useEffect+fetch — no RSC data fetching, no SWR/React Query, ~40 duplicated loading/error scaffolds.
  • XP awards aren't atomic and race — concurrent awards clobber each other (last-write-wins on absolute values).
  • Whisper — your most cost-critical external call — has no timeout and no retry, while the image clients do.
  • Migration journal is broken: 0050–0054 untracked; a fresh environment running db:migrate would be missing five migrations' worth of tables.
  • Safety nets are all off: ignoreBuildErrors, ESLint mostly disabled, no tests — 79 real type errors ship silently, including one cluster that's a latent logic bug.

2The five things to fix first

Critical1. IDOR: any teacher can take over any student account

The regenerate-token route checks only role, never ownership. Any teacher (or admin) can regenerate the permanent login token of any student in the school — across classes and teachers — and the response hands back the new token. Since /s/[token] converts that token into a passwordless session, this is full impersonation of a minor's account. Ownership helpers (userCanAccessStudentMedia, enrollment checks) already exist and are used elsewhere; this route just skips them.

src/app/api/teacher/students/[studentId]/regenerate-token/route.ts:12–32 → src/app/s/[token]/route.ts
Critical2. Unauthenticated roster + visual-password-type leak

Two class-scoped routes return full student names and visualPasswordType with no getCurrentUser() at all. The sibling /api/students route was explicitly hardened against this exact leak (the fix comment describes the account-takeover chain), but these two were missed. With the ~12-option visual-password keyspace, leaking the type materially narrows brute force, and the only prerequisite is a classId — obtainable from a /c/[shortCode] link.

src/app/api/classes/[classId]/students/route.ts:31–50 · src/app/api/classes/[classId]/students/[studentId]/route.ts:41–66
High3. Missing indexes on the two hottest access paths

The classes table has zero indexes on teacher_id, school_id, or term_id — yet accessibleClassIds() filters on teacher_id on essentially every teacher/admin request (sequential scan). Likewise class_enrollments only has a composite unique index led by classId, so the very common WHERE student_id = ? lookups on every student page can't use it. Two CREATE INDEX statements fix the two most frequent queries in the app.

src/lib/db/schema.ts:218–251 (classes) · schema.ts:253–264 (class_enrollments) · src/lib/auth/class-access.ts:115–121
High4. Migration journal missing 0050–0054

migrations/meta/_journal.json ends at 0049, but the folder contains 0050–0054 (multibook practice units, teacher capabilities, generated tests, longitudinal progress, gradebook). They were applied out-of-band, so any fresh environment — or anyone trusting db:migrate — silently misses five migrations' worth of tables. There's also a duplicate 0007_* prefix collision (one journaled, one orphaned hand-written file). Worth reconciling the journal once and picking a single workflow.

migrations/meta/_journal.json · migrations/0050–0054*.sql · migrations/0007_add_story_tts_versions.sql vs 0007_graceful_nomad.sql
High5. XP awards: non-atomic and a lost-update race

awardXp() runs 5–9 sequential queries (event insert, progression upsert, unlocks, then a loop of star writes) with no transaction — a mid-sequence failure leaves XP events without balance updates or diverged star ledgers. Worse, it reads progression into JS, computes new totals, and writes absolute values back: two concurrent awards for the same student clobber each other, losing XP and corrupting streak/level. Notably awardStars already does this correctly with SQL increments — the fix pattern is in the same folder.

src/lib/gamification/award.ts:62–222 (esp. 74–84 read, 136–145 absolute write) · contrast src/lib/gamification/stars.ts:64–65

3Security & API layer

180 routes, each self-enforcing auth (middleware is pass-through by design). Where the centralized helpers are used (~58 routes), authorization is solid — including co-teacher awareness and existence-oracle avoidance. The problems are the routes that skip them, and the sheer volume of duplicated boilerplate that makes skipping easy.
